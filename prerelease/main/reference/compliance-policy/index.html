Compliance policy

Compliance policy

The contract of the Rego compliance policy: how and where it runs, its input and decision, how its findings are reported, and when it fails.

The compliance policy is the deterministic part of Kumoss’s compliance check: a Rego module that Open Policy Agent (OPA) evaluates against the plan of every generate round. No language model is involved, so the same plan always gets the same verdict. A deny finding locks the session.

This page is the contract a policy follows. To add a rule step by step, see Write a policy rule. For how the policy relates to the other checks that can lock a session, see How compliance works.

How the policy runs

At the end of every generate round, when orchestration.enable_compliance_checker is true:

  1. The core fetches the version of the policy that carries your environment’s label in Langfuse. Nothing is cached, so a label moved in Langfuse applies to the next round.

  2. It builds the input document from the round’s final plan and the root module’s providers, and runs one opa process on it (OPA 1.22.4, shipped in the core image):

    opa eval --stdin-input --strict-builtin-errors --format json \
  --data compliance.rego data.kumoss.compliance

  3. It reads the decision: blocking deny findings, non-blocking warn findings, and the list of rules checked.

  4. The language-model audit runs next, and both results are merged into one compliance report for the round; see How findings appear in the report.

  5. If either part has an error or critical finding, the session is locked and the compliance failure notification is sent.

Drift and import rounds are never checked.

Where the policy lives

The policy is the Langfuse text prompt general/policies/compliance, seeded from core/prompts/seed/general/policies/compliance.rego. The core uses the raw text of the version: Langfuse’s {{variable}} templating is not applied, so the braces of Rego are safe. A version you customized is never overwritten by a Kumoss upgrade. How versions, labels, and seeding work is in How seeding works.

Input

The document the policy receives as input:

{
  "plan": { ... },
  "kumoss": {
    "schema": "kumoss.compliance.input/v1",
    "providers": ["azurerm", "kubernetes"]
  }
}
Field Content

input.plan

The final plan’s terraform show -json or tofu show -json document, unchanged. Rules usually walk input.plan.resource_changes.

input.kumoss.schema

kumoss.compliance.input/v1. Changes if the shape of input ever does.

input.kumoss.providers

The provider type names of the root module’s required_providers (azurerm for hashicorp/azurerm). Use it to scope rules to the providers a module actually uses; see Root module manifest.

Three properties of the plan limit what a rule can check:

  • It is a -target plan: it holds the session’s targets only, so a rule cannot see resources outside them.

  • Values known only after apply are absent from after and listed in after_unknown.

  • It carries sensitive values unmasked. Never put attribute values in a finding’s message, which ends up in the compliance report, the session’s artifacts, and the notification; name the resource address and the attribute instead.

Decision

The core queries data.kumoss.compliance, so the module must declare package kumoss.compliance. All keys are optional; a missing one counts as empty, and keys outside these three are ignored.

Key Type Meaning

deny

set of {rule_id, message, resource?, severity?}

Blocking findings. severity is error (the default) or critical.

warn

set of {rule_id, message, resource?}

Non-blocking findings, reported with severity warning.

rules

set of strings

Every rule id the policy evaluates, so the report lists the rules that passed too. Rule ids of findings are added to it anyway.

rule_id and message are non-empty strings; resource, when present, is a string, usually the resource address.

How findings appear in the report

The policy’s decision and the language-model audit are merged into one compliance report per round:

  • Each policy violation carries source: "opa"; findings of the audit carry "llm", and reports stored before the policy existed have no source. The web application marks policy findings with a policy badge.

  • The policy’s findings come first.

  • policy_revision is the version that ran, as "<prompt name>@<version>", for example general/policies/compliance@4, or null when no policy ran.

  • passed is false when either source has an error or critical finding, and the session is then locked as for any failed compliance check. When the policy is what blocks, the summary starts with Blocked by the compliance policy: N finding(s) (<rule ids>).

When the policy cannot be evaluated

The policy fails closed. If it cannot be evaluated, the round gets a blocking policy_unavailable finding (severity error) whose message gives the reason, so the session is locked and the compliance failure notification is sent. The language-model audit still runs, and its findings are in the same report.

Problems in the policy

Fix these in a new version of the policy:

  • A syntax or compile error.

  • No package kumoss.compliance, or data.kumoss.compliance is not an object.

  • deny, warn, or rules is not a set; a finding is not an object or lacks rule_id or message; or a deny severity is neither error nor critical.

  • A builtin error. The policy runs with --strict-builtin-errors, so to_number("x") fails rather than being undefined.

  • The evaluation did not finish within 30 seconds.

Problems around the policy

These need your operator:

  • The policy could not be fetched from Langfuse: Langfuse is unreachable, the prompt or a version carrying the environment label does not exist, or that version is not a single text prompt.

  • The plan JSON could not be read.

  • opa could not be run.

Startup check

When enable_compliance_checker is true, the core evaluates the current policy against an empty plan after seeding the prompts, and refuses to start if that fails: a missing opa binary, a broken policy, or Langfuse unreachable. A broken version that gets the environment label while the core is running is caught only when it is evaluated, and then blocks every round.

The shipped rule

The seed defines one rule, critical_deletion (severity critical): a managed resource whose plan actions are exactly ["delete"] is denied, even when the user requested the deletion. A replacement (["delete", "create"] or ["create", "delete"]), a forget (a removed block with destroy = false), and data sources are allowed. Its code, explained line by line, is in How a rule works.

Write your own rules

Rules for the providers your modules use (no public storage, no owner role assignments, allowed regions) are added to the same module. See Write a policy rule.

Testing commands

All commands use the OPA image at the version the core ships. With OPA 1.22.4 installed locally, run opa with the same arguments instead.

Run the shipped rule’s tests, from the repository root:

docker run --rm -v "$PWD/core:/core:ro" -w /core \
  openpolicyagent/opa:1.22.4-static \
  test prompts/seed/general/policies tests/policies

The fixtures in core/tests/policies are real Terraform 1.16 and OpenTofu 1.13 plans, fixtures/<engine>/data.json, which opa test loads as data.fixtures.<engine>.

Check that a policy compiles, from the folder that holds compliance.rego:

docker run --rm -v "$PWD:/w:ro" -w /w \
  openpolicyagent/opa:1.22.4-static check compliance.rego

Evaluate a policy against an input document, as the core does:

docker run --rm -i -v "$PWD:/w:ro" -w /w openpolicyagent/opa:1.22.4-static \
  eval --stdin-input --strict-builtin-errors --format pretty \
  -d compliance.rego data.kumoss.compliance < input.json

How to build input.json from a plan is shown in Write a policy rule.
