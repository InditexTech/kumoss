= Quickstart
:description: Install Kumoss on one machine with Docker Compose, from cloning the repository to opening the running web application.

In this quickstart, you install Kumoss on one machine with Docker Compose,
using the bundled stack as shipped, and open the running web application.

== Prerequisites

Before you begin, make sure you meet the
xref:main:prerequisites.adoc[prerequisites].

== Step by step

=== 1. Clone the repository and create the environment files

[source,bash]
----
git clone https://github.com/InditexTech/kumoss.git
cd kumoss

cp core/env.sample core/.env
cp services/iac/env.sample services/iac/.env
----

Each `env.sample` documents its own variables and is the source of truth
for their names. Every `.env` file is gitignored; never commit one.

=== 2. Write config.yaml

`config.yaml` at the repository root is the single configuration file. It
is baked into the core image at build time, so every edit needs
`docker compose build core`.

The minimum is the two model strings for your LLM provider and the two
orchestration gates. Fields not shown use the core's code defaults; use the
shipped file or the configuration reference when you need its non-default
tuning.

The `llm` values below are only an example: replace both model strings with
the models you prefer. Model strings per provider:
xref:main:reference/llm-providers.adoc[LLM providers and models].

[source,yaml]
----
llm:
  model: "vertex_ai/claude-sonnet-4-5"
  small_model: "vertex_ai/gemini-3.8-flash"

orchestration:
  enable_compliance_checker: true
  block_on_high_impact: true
----

Apart from the Git credentials you set in the next step, you may need to
change the Git provider. `git.provider` must name the host of your
repository and defaults to `GITHUB`; for Azure DevOps or GitLab, add it to
the file:

[source,yaml]
----
git:
  provider: "GITLAB"  # or "AZURE_DEVOPS"
----

Accepted values and the supported hosts:
xref:main:reference/configuration.adoc#config-git[`git` configuration].

=== 3. Fill in core/.env

Set:

* *LLM provider credentials* — the variables LiteLLM reads for the
  provider prefix of `llm.model` and `llm.small_model`. See
  xref:main:reference/llm-providers.adoc#provider-credentials[provider
  credential variables]. The core will not run without them.
* `GIT_USER`, `GIT_TOKEN` — the account and personal access token for the
  provider named by `git.provider` defined in the above `config.yaml`.

Keep the remaining sample values: they match the bundled containers. Every
variable: xref:main:reference/environment-variables.adoc[Environment
variables and secrets].

=== 4. Fill in services/iac/.env

Set:

* *Cloud provider credentials* — the variables your OpenTofu or Terraform
  providers read. See
  xref:main:reference/terraform-providers.adoc[Terraform providers] for
  the minimum set per cloud and authentication method.

The sidecar runs OpenTofu {opentofu-version} by default. Set
`IAC_BINARY=terraform` to use the bundled HashiCorp Terraform
{terraform-version} instead; it is BUSL-1.1 licensed, and selecting it
makes your use subject to that license.

Invalid or missing cloud credentials do not stop the container. The engine
runs anyway and its own authentication error appears in the session as a
failed `init`, `plan`, or `apply`.

=== 5. Build and start Kumoss

[source,bash]
----
docker compose up --build
----

Add `-d` to run in the background. The first build downloads the base
images, installs the Python dependencies, downloads both IaC engines, and
compiles the web application.

After a later change to `config.yaml`, rebuild and restart the core:

[source,bash]
----
docker compose build core
docker compose up -d core
----

A change to a `.env` file needs the affected container recreated
(`docker compose up -d core`, `docker compose up -d iac`); `docker compose
restart` does not reload it.

=== 6. Verify the services

[source,bash]
----
docker compose ps
docker compose logs -f core
----

Wait for `Application startup complete` in the core log. Boot is strict:
if a start-up step fails, the container exits with the reason in the log.
A `notifications` container that has exited is expected while that
optional sidecar is unconfigured.

[source,bash]
----
curl http://localhost/api/v1/auth/config
----

With authentication disabled this returns a JSON document with an empty
`issuer_url`.

== See it working

[cols="1,3",options="header"]
|===
|URL |What it serves

|`\http://localhost`
|Kumoss web application and the API under `/api/v1/...`

|`\http://localhost/monitoring/`
|Phoenix: traces of every run and the prompt registry

|===

Port 80 serves the unauthenticated Kumoss application by default, while
port 9000 exposes presigned artifact downloads, on every interface of the
host. Keep the stack on a machine only you can reach. The RustFS web
console is disabled; to enable it, see
xref:main:guides/production/operations.adoc#rustfs-console[RustFS
console].

Open `\http://localhost`. With authentication disabled you land directly in
the wizard as the local developer. Enter a repository your Git token can
push to, choose the cloud and scope, describe the infrastructure you need,
and follow the session. What each mode does is explained in
xref:main:guides-overview.adoc[Guides]; your sessions and the admin panel
are described in
xref:main:guides/administer-users-and-locks.adoc[Administer users and
locks].

Open `\http://localhost/monitoring/` to see the traces of the run and the
seeded prompts under *Prompts*. Phoenix receives prompts, plans, and
generated code in clear text and has no authentication of its own in this
stack; see xref:main:guides/monitor-with-phoenix.adoc[Monitor with
Phoenix].

== Stop or reset the stack

[source,bash]
----
docker compose down            # stop; named volumes are kept
docker compose down -v         # stop and delete all volumes
----

`down` keeps the databases, artifacts, and workspaces, so sessions and
prompts survive a restart.

*`down -v` deletes the session database, the artifacts, the Phoenix traces
and prompts, and any in-progress workspaces* — and, by default, the
Terraform state too, since Kumoss manages it in that same object-storage
volume. State survives only if you set `storage.terraform_state_bucket` to
`""` so that each repository declares its own backend instead.

== Troubleshooting

* *The core exits during boot.* Boot is strict and the reason is in
  `docker compose logs core` — most often missing LLM credentials, an
  empty `KUMOSS_IAC_TOKEN` or database URL in `core/.env`, or Phoenix not
  yet reachable. The stack has no healthchecks, so a dependency that was
  simply slower to start leaves the core stopped rather than retrying: run
  `docker compose up -d core` again.
* *Every session fails at validation with a `401` from the IaC sidecar.*
  `KUMOSS_IAC_TOKEN` differs between `core/.env` and `services/iac/.env`.
* *A `config.yaml` change has no effect.* Rebuild the core image with
  `docker compose build core`.
* *`plan` or `apply` fails with a provider authentication error.* The cloud
  credentials in `services/iac/.env` are absent, invalid, or insufficient.
* *`plan` fails with `permission denied` on a file in the workspace.* The
  `workspaces` volume predates the current non-root containers. Run
  `docker compose down`, then `docker run --rm -v kumoss_workspaces:/workspaces
  alpine chown -R 10001:10001 /workspaces`, and start again.
* *`init` fails on the state backend, or every plan wants to recreate
  existing resources.*
  xref:main:guides/configure-state-backends.adoc#state-troubleshooting[Troubleshooting
  state backends].
* *Push or pull-request creation fails.* Check `GIT_USER`, `GIT_TOKEN`,
  that `git.provider` matches the repository host, and the token's
  permissions.
* *A session aborts because a prompt is missing.* The prompt is absent from
  Phoenix or has no version tagged with the `environment` value. See
  xref:main:guides/customize-prompts.adoc[Customize prompts].
* *The browser cannot download an artifact.* Port 9000 must be reachable
  from the browser under the host in `storage.public_endpoint_url`.
* *LLM calls fail although the core booted.* Not every provider can be
  validated at boot. See
  xref:main:reference/llm-providers.adoc#llm-troubleshooting[LiteLLM
  troubleshooting].
