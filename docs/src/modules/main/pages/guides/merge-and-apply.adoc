= Merge and apply
:description: Open the pull request for a Kumoss session, merge it, and apply the reviewed plan.

Once you have reviewed a session's results, this guide takes you from the
session branch to applied infrastructure: you open the pull request, get
it reviewed, merge it, and apply exactly the plan you reviewed. If a
*Deployment Blocked* screen opens on the way, see <<session-locked>>.

== Prerequisites

* A session with results, reached by following
  xref:main:guides/follow-a-session.adoc[Follow a session].
* The `developer` role; see
  xref:main:reference/roles-and-permissions.adoc[Roles and permissions].

== Steps

. In the results view, choose *Create PR*.
+
Kumoss writes the title and description and opens the pull request from
the session branch on your Git provider. This can take a minute. When it
is ready you see "Here is your Pull Request."

. Choose *View Pull Request* and review it with your team.
+
The button appears when the link points at a recognized Git host;
otherwise copy the link from the session details. Your team's normal
review and CI apply. To make changes, type them as a follow-up request:
the new round pushes to the same branch and updates the pull request.

. When the review is done, choose *Approve PR and Apply*, then *Confirm
  and Apply*.
+
The confirmation asks you to confirm that you read and understood the
report and the proposed changes. *Confirm and Apply* merges the pull
request into the default branch and starts the apply; to ask for help
instead, choose *Request Review*, which sends a support request.
+
The engine executes exactly the plan you reviewed; it is not re-planned.
The apply-results screen shows *Succeeded*, *Partially Applied*, or
*Failed*, with the execution summary, the resources created, updated,
destroyed, or failed, and recommendations.

NOTE: In drift-remediation and import sessions the button reads *Approve
and Merge PR* and only merges: the merge is the remediation, an import is
already in the state, and no apply follows. See
xref:main:reference/operating-modes.adoc#compare-modes[Comparing the operating modes].

[#session-locked]
== If the session is locked

If the *Deployment Blocked* screen opens instead of the merge controls,
the session is locked: you can still create the pull request, but merge
and apply are refused. Expand *Why* to see what locked it.

.The Deployment Blocked screen with *Why* expanded: a high-impact verdict, a `critical_deletion` finding from the compliance policy, and a `scope_exceeded` finding from the compliance audit
image::deployment-blocked.png[Deployment Blocked screen listing the high-impact reason and two blocking compliance findings, with Back to Report, Contact Team, and Check again buttons,width=560,link=self]

See xref:main:guides/resolve-a-locked-session.adoc[Resolve a locked
session] for what each cause means and how to get the session unlocked.

== Verify

* The apply-results screen shows *Succeeded*.
* The pull request shows as merged into the default branch on your Git
  provider.

The session's own status is not a reliable check: a failed apply also
ends the session normally. A failed apply is not retried and nothing is
rolled back; read the error on the apply-results screen and start a new
request.

After an apply the reviewed plan is consumed. To change anything else,
send a new request; a fresh plan is produced and reviewed before the
next apply.
