xref:main:guides/write-a-policy-rule.adoc[Write a policy rule]= Resolve a locked session
:description: Find out why Kumoss locked your session, who was notified, and how to get it unlocked so you can merge and apply.

Kumoss checks every generate round before it lets you merge and apply.
When a check fails, the session is locked: you can keep working on it,
but merge and apply are refused until the lock is cleared. This guide
explains why a session gets locked, what you see, and the two ways to
get it unlocked.

== Prerequisites

* A session whose latest generate round finished, reached by following
  xref:main:guides/follow-a-session.adoc[Follow a session].
* To unlock a session yourself, the panel role `editor` or `admin`; see
  xref:main:reference/roles-and-permissions.adoc[Roles and permissions].
  Without it, you need a follow-up request or a reviewer who has it.

[#why]
== Why a session is locked

Three independent checks run at the end of every generate round, and any
one of them can lock the session. Only the first is deterministic: the
same plan always gets the same verdict. The other two are judgments made
by a language model, because they depend on what you asked for and on
what a change means, which no fixed rule over the plan can capture.
For the mechanism as a whole, see
xref:main:architecture/compliance.adoc[How compliance works].
Drift and import rounds are never checked and never lock a session.

All three are prompts in Langfuse, seeded from
`core/prompts/seed/general/` (and, for the provider policies, from
`core/prompts/seed/<provider>/`). A change takes effect on the next generate
round once its new version carries your environment's label. Which
checks run at all is set by your operator with the `orchestration`
switches; see xref:main:reference/configuration.adoc[Configuration].

[#compliance-policy]
=== Compliance policy (deterministic)

*What locks.* Open Policy Agent evaluates your organization's
xref:main:reference/compliance-policy.adoc[compliance policies], Rego
modules, against the plan's JSON: the general policy, and one policy
for each provider the module declares. Any `deny` finding locks the
session; `warn` findings are reported but do not.

* The general policy's `critical_deletion` rule denies any resource
  that is destroyed without being recreated, *even when you asked for
  the deletion*. Replacements are allowed.
* The other shipped rules deny removing a customer-managed key, having
  Terraform run commands (provisioners, `null_resource`, external data
  sources), and provider-specific risks such as public ingress or
  wildcard admin roles; see
  xref:main:reference/compliance-policy.adoc#shipped-rules[The
  shipped rules].
* If a policy cannot be evaluated at all, the round gets a
  `policy_unavailable` finding and is locked too: the policies
  xref:main:reference/compliance-policy.adoc#failure[fail closed].

Findings from this check carry a *policy* badge.

*Why it is deterministic.* No model is involved: the rules are code that
reads resource types, actions, and attribute values from the plan. The
same plan always gets the same verdict, and every rule can be tested
with `opa test` before it is rolled out.

*Where to change it.* The general policy is the Langfuse prompt
`general/policies/compliance`, and each provider's is
`<provider>/policies/compliance`, seeded from
`core/prompts/seed/<scope>/policies/compliance.rego`. To add a rule, such
as allowed regions, no public storage, or no owner role assignments,
write it in the policy of the provider it concerns (or in the general
policy when it spans providers), test it, and publish it as a new
version in Langfuse; see
xref:main:guides/write-a-policy-rule.adoc[Write a policy rule]. The
input a policy receives and the decision it must return are in
xref:main:reference/compliance-policy.adoc[Compliance policy].

Use the policies for every rule you can state as a condition on the
plan: they are the only check that cannot miss a case or flag one by mistake.

[#compliance-audit]
=== Compliance audit (not deterministic)

*What locks.* A language-model agent compares the plan with every
request of the session and with your organization's conventions, and
reports violations with a rule id and a severity. A finding of severity
`error` or `critical` locks the session; `warning` is reported only. The
shipped rules are:

* `scope_exceeded`: the plan changes something you did not ask for, for
  example it removes a block or sets an attribute to null. A removal is
  never accepted as a side effect of an addition.
* `scope_incomplete`: part of your request has no matching change in
  the plan.

Other findings come from the conventions the model checks the plan
against, for example a missing mandatory tag.

*Why it is not deterministic.* Whether a change is "what you asked for"
depends on the meaning of your request, written in natural language;
there is no attribute in the plan to test. The same holds for
conventions written as prose. A model can read both, but two runs on the
same plan can disagree, so a finding can be wrong. When you think it is,
rephrase the request to be explicit about what must change and what must
stay, or ask a reviewer to check it.

*Where to adapt it.* Two kinds of prompts drive the audit:

* `general/compliance/report` defines the business rules, each with a
  `rule_id` and a severity. Edit `scope_exceeded` and `scope_incomplete`
  to match how strict your organization wants to be, or add your own
  rules in the same format; see
  xref:main:guides/customize-prompts.adoc#compliance-prompts[Compliance
  prompts].
* The convention prompts are the standards the plan is checked against:
  `general/guidelines/terraform` and, per provider, `resource_creation`,
  `networking`, and `permissions`; see
  xref:main:guides/customize-prompts.adoc#general-guidelines[General
  cross-provider prompts] and
  xref:main:guides/customize-prompts.adoc#provider-guidelines[Provider-wide
  guidelines]. The same prompts guide the generator, so a standard written
  there is followed when code is written and checked when it is audited.

If a convention can be stated as a condition on the plan, write it as a
rule of the xref:main:reference/compliance-policy.adoc[compliance
policy] instead: it then always holds, without depending on the model.

[#high-impact]
=== High impact (not deterministic)

*What locks.* While writing the report, the report model groups the
changes and labels each group `low`, `medium`, or `high`, and the report
shows the overall level as its impact banner. When the level is `high`
and your deployment enables `orchestration.block_on_high_impact`, the
session is locked. The banner is shown on every report either way.

*Why it is not deterministic.* Whether a change causes downtime or
touches something critical depends on the resource, the attribute, and
its context: renaming a tag and changing a firewall rule are both
in-place updates in the plan. A model makes that judgment from written
criteria, so the same plan can be rated differently on two runs.

*Where to adapt it.* The criteria are the prompt
`general/compliance/impact`. The shipped criteria are: high for
destructive actions, restarts, service downtime, or critical networking
changes; medium for configuration updates that change behavior without
guaranteed downtime; low for isolated new resources or non-disruptive
updates such as tags or locks. Rewrite them to match your organization's
change-management standards, for example to rate any change to a
production network as high; see
xref:main:guides/customize-prompts.adoc#compliance-prompts[Compliance
prompts].

If a specific change must always be stopped, such as any change to a
firewall, write it as a rule of the
xref:main:reference/compliance-policy.adoc[compliance policy]: a
high-impact verdict is a model's judgment and is not guaranteed.

[#what-you-see]
== What you see

When you continue to the pull request, the *Deployment Blocked* screen
opens instead of the merge controls; see the screenshot in
xref:main:guides/merge-and-apply.adoc#session-locked[Merge and apply].

* Expand *Why* to see the cause: *High impact* with the impact summary,
  *Compliance* with each blocking finding (severity, rule id, and
  resource), or both. *Show all findings* adds the warnings and the
  suggested fixes.
* *Check again* reads the lock state again, for example after a
  reviewer unlocked the session.
* *Back to Report* returns to the report. *Contact Team* sends a support
  request.

The full compliance report, including the rules that passed, is also in
the session details, as the round's *Compliance Check* artifact.

While locked, you can still read everything, continue the conversation,
and create the pull request so reviewers can read the diff. Merge and
apply are refused with `409`. Your sessions list shows the lock in the
*Apply* column.

[#who-is-notified]
== Who is notified

When the notifications sidecar is enabled, Kumoss sends a "Compliance
check failed" notification, a "High impact changes detected"
notification, or both. They go to you and to every user with the panel
role `editor` or higher, so a reviewer usually knows about the lock
before you ask.

If your browser tab is hidden when the round finishes, you also get a
"Session blocked" browser notification.

[#unlock]
== Unlock the session

Choose one of the two ways:

. *Fix the request.* Read the findings under *Why*, then send a
  follow-up request that addresses them, for example "keep the existing
  bucket and only add the tag". When the new round passes all three
  checks, the lock clears and the merge controls return.
. *Ask a reviewer.* A user with the panel role `editor` or `admin`
  reviews the findings in the admin panel and unlocks the session; see
  xref:main:guides/administer-users-and-locks.adoc#unlock-a-session[Lock
  or unlock the apply of a session]. When they are done, choose *Check
  again*.
+
.A reviewer opens the locked session from the admin panel's Sessions tab and presses *Apply Locked* to unlock it
image::admin-unlock-session.png[Admin panel Sessions tab with the locked session's detail panel open and the Apply Locked button highlighted,link=self]

NOTE: A reviewer's unlock lasts only until your next generate round on
the session. That round runs the checks again and sets the lock afresh.

== Verify

The *Deployment Blocked* screen no longer opens when you continue to the
pull request, the *Apply* column of your sessions list shows the session
unlocked, and *Approve PR and Apply* is available. Continue with
xref:main:guides/merge-and-apply.adoc[Merge and apply].
