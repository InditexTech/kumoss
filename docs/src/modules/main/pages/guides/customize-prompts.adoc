= Customize prompts
:description: Adapt Kumoss to your organization's standards by editing its prompts in Langfuse: what each prompt controls, how to change one safely, how to add a resource prompt, and how to write exception lists.

Kumoss does not hard-code cloud knowledge. Its agents read your
organization's standards (naming, tagging, networking, permissions,
compliance rules, and exceptions) from *prompts* stored in
https://langfuse.com/docs/prompt-management[Langfuse]. This guide shows
what each prompt controls and how to change it. How the registry works
underneath, including seeding and the shipped inventory, is in
xref:main:reference/prompt-registry.adoc[Prompt registry].

== Prerequisites

* Access to your deployment's Langfuse with a role that can edit
  prompts; see xref:main:guides/monitor-with-langfuse.adoc[Monitor with
  Langfuse] for where it runs and how to log in.
* Your deployment's `environment` value (`development` by default). The
  core reads every prompt from the version carrying that label; see
  xref:main:reference/configuration.adoc[Configuration].

[#what-you-can-customize]
== What you can customize

Every prompt is named `<scope>/<type>/<name>`, where the scope is
`general` or a Terraform provider type such as `azurerm`. Provider
prompts apply only to sessions whose root module uses that provider.
For which agent reads each prompt, see
xref:main:reference/prompt-registry.adoc#prompt-composition[Which agent
reads which prompt].

[#general-guidelines]
=== General guidelines

[cols="2,4",options="header"]
|===
|Prompt |What it controls

|`general/guidelines/terraform`
|Organization-wide Terraform standards: structure, providers, state,
and style. Followed by the code generator and checked by the compliance
audit. Do not write into it bans a compliance policy enforces; see
<<compliance-policy>>.

|`general/guidelines/requests`
|Which requests the request filter accepts, declines, or answers.

|`general/guidelines/targeting_policies`
|Resources a partial drift round must never plan. Ships as a
placeholder with no exclusions.
|===

[#provider-guidelines]
=== Provider guidelines

One set per provider, at `<provider>/guidelines/<name>`:

[cols="2,4",options="header"]
|===
|Prompt |What it controls

|`resource_creation`
|General conventions for creating resources: tags, naming, and
defaults. Followed by the generator and checked by the audit.

|`networking`
|Networking conventions: address plans, exposure rules, and private
endpoints. Followed by the generator and checked by the audit.

|`permissions`
|Identity and access conventions: least privilege and role assignment
patterns. Followed by the generator and checked by the audit.

|`abbreviations`
|Short prefixes for resource names.

|`resources_list`
|The catalog of resource prompts the session may use; see
<<add-a-resource-prompt>>.

|`drift_exceptions`
|What drift remediation must never touch; see
<<drift-exception-rules>>.

|`import_exceptions`
|Resource IDs an import must never bring under Terraform; see
<<import-exception-list>>.
|===

[#resource-prompts]
=== Resource prompts

`<provider>/resources/<name>` holds the default configuration of one
resource type, such as `aws/resources/s3_bucket` or
`azurerm/resources/storage_account`, used unless the request asks for
something else. A session uses only the resource prompts its request
needs, chosen from `resources_list`.

[#compliance-prompts]
=== Compliance prompts

[cols="2,4",options="header"]
|===
|Prompt |What it controls

|`general/compliance/report`
|The business rules the compliance audit checks a plan against, each
with a rule id and a severity. Ships with `scope_exceeded` and
`scope_incomplete`. A failed check locks the session.

|`general/compliance/impact`
|What counts as a low, medium, or high impact change. A high impact
locks the session when `orchestration.block_on_high_impact` is `true`.

|`general/policies/compliance`
|The general deterministic compliance policy, in Rego, evaluated on
every generate round; see <<compliance-policy>>.

|`<provider>/policies/compliance`
|A provider's compliance policy, in Rego, evaluated with the general
policy when the root module declares that provider; see
<<compliance-policy>>.
|===

For how these checks decide whether a session is locked, see
xref:main:architecture/compliance.adoc[How compliance works]; for what
each one looks for, see
xref:main:guides/resolve-a-locked-session.adoc#why[Why a session is
locked].

[#change-a-prompt]
== Change a prompt

. In Langfuse, go to *Prompts* and open the prompt, for example
  `azurerm/guidelines/resource_creation`.
. Create a new version with your edited text. When Langfuse offers to
  set labels, leave your production environment's label unticked.
. Try the version on a deployment whose `environment` is `development`
  or `staging`: set that environment's label on the new version and run
  a session that exercises the change.
. Move your environment's label to the new version. The next session
  uses it; no restart is needed.

To roll back, move the label back to the previous version. Keep earlier
versions for that reason.

WARNING: Never move or remove the `seed` label. It marks the version the
seeder last pushed; without it, the next startup treats your latest
version as its own. See
xref:main:reference/prompt-registry.adoc#how-seeding-works[How seeding
works].

=== Verify

Run a session that touches the change, and check that the generated
code, the report, or the compliance findings follow it. If they do not,
check that the label sits on the version you edited.

=== What happens on upgrades

A Kumoss release that changes a shipped prompt only moves the
environment labels that are still on the shipped version. Once you move
a label to your own version, upgrades leave it there, and merging later
shipped changes into your version is up to you.

[#add-a-resource-prompt]
== Add a resource prompt

A resource prompt is only used if `resources_list` names it. Add both
in Langfuse:

. Create a *text* prompt named `<provider>/resources/<name>`, for
  example `aws/resources/cloudfront_distribution`, with the default
  configuration as its body. Set your environment's label on it.
. Open `<provider>/guidelines/resources_list`, create a new version with
  one more line, and set your environment's label on it:
+
[source,markdown]
----
- `cloudfront_distribution` — CloudFront distribution with HTTPS only and an origin access control.
----
+
The name must equal the `<name>` part of the prompt exactly. Follow the
style of the existing lines; the Kubernetes list uses plain bullets
without backticks.
. Run a session that asks for the new resource.

Both prompts must exist: a resource prompt missing from
`resources_list` is never selected, and a `resources_list` entry
without a prompt contributes nothing.

=== Ship it with the image instead

To make the prompt part of every new deployment, add it as seed files:

. Create `core/prompts/seed/<provider>/resources/<name>.yaml` with
  `description` and `body`; see
  xref:main:reference/prompt-registry.adoc#seed-files[Seed file
  conventions].
. Add the `<name>` entry to
  `core/prompts/seed/<provider>/guidelines/resources_list.yaml`.
. Rebuild the core image (`docker compose build core`) and start the
  stack. The seeder creates the new prompt, labeled with every
  environment.

[#drift-exception-rules]
== Write drift exception rules

`<provider>/guidelines/drift_exceptions` is the list of things drift
remediation must never touch. A dedicated *drift exception filter*
reads it on every drift round, full or partial, and on the drift
pre-check inside every generate round, so a generate round cannot
"fix" an excluded resource either. The filter receives the drift
operations that remain after the session's own changes are removed, and
returns the ones no rule covers; only those are remediated.

Whatever it removes is reported in the drift report under *Left Alone
by Exception Rules*, naming the change and the rule that covers it.
Leaving an excluded change alone is the intended result, so it does not
lower the report's outcome. See
xref:main:guides/remediate-drift.adoc#drift-report[Read the drift
report].

This is not the same as `general/guidelines/targeting_policies`, which
decides which resources a *partial* drift round plans at all. Exception
rules apply to the operations of every drift round, whatever produced
them.

=== How to write one

The body is prose, read by a model. Keep each exception on its own
bullet, and name the resource address, type, attribute, tag, namespace,
or naming pattern precisely enough to match a sentence like "In
`main.tf`, for `azurerm_key_vault.kvt_001`: update the tag `owner` from
`platform` to `payments`." Say what must not be reconciled, and why:
the reason is what the report quotes back.

The shipped seed has three sections, the rule kinds the filter
understands:

* *Provider quirks*: a permanent false diff the provider reports on
  every plan.
* *Resources managed outside Terraform*: something another system owns
  and changes on purpose.
* *Environment, team, and naming carve-outs*: whole slices of the estate
  a workload session must not touch.

The filter may also *trim* an operation: when one instruction bundles
an excluded change with a legitimate one, it keeps the legitimate part.
Rules that name a single attribute are therefore as useful as rules
that name a whole resource.

=== Example

[source,markdown]
----
## Provider quirks (permanent false diffs)
- The `azurerm` provider always reports a diff on the `created_at` tag
  written by the tagging policy; never reconcile that tag.

## Resources managed outside Terraform
- The values of `azurerm_key_vault_secret` are rotated by the secrets
  platform; never reconcile them.

## Environment, team and naming carve-outs
- Never reconcile resources in the `rg-shared-platform` resource
  group; the platform team owns them.
----

With these rules, a drift round that finds "Delete resource
`azurerm_storage_account.sta_shared_001` in `rg-shared-platform`"
remediates nothing and lists the resource under *Left Alone by
Exception Rules*, quoting the carve-out, with the outcome still
*Succeeded*.

[#import-exception-list]
== Write the import exception list

`<provider>/guidelines/import_exceptions` names the resources an import
round must never bring under Terraform, even when they exist in the
cloud scope and the state does not track them. Unlike every other
prompt, it is not read by a model: the core parses it and removes the
listed IDs from the scope before anything else sees it.

* The list applies on *every* import round, full scope or partial. A
  withheld resource never reaches the selection agent, the code
  generator, or `terraform import`, so neither a broad request nor a
  model can bring it back.
* Azure resource IDs match case-insensitively, so
  `/subscriptions/.../resourceGroups/rg-a` also withholds
  `/resourcegroups/RG-A`. GCP and AWS IDs match exactly.
* Withheld resources are not an error: the import report names each one
  as skipped on purpose. When every unmanaged resource in the scope is
  withheld, the round ends with `Every unmanaged resource in the scope
  <scope> is on the import exception list.` and an empty report.
* An ID that is not in the scope, or is already managed, has no effect.

Only Azure, GCP, and AWS scopes can be listed for import, so the list
is read for `azurerm`, `google`, and `aws` only.

=== How to write one

Put each resource ID on its own Markdown bullet (`-` or `*`), exactly
as the cloud's scope listing returns it: the full ARM ID for Azure, the
asset name without the `//service.googleapis.com/` prefix for GCP (for
project IAM, the space-separated `<project-id> <role> <member>` entry),
and the ARN for AWS. See xref:main:reference/api/iac.adoc[IaC sidecar
API] for the exact shapes. Backticks around the ID are optional. Every
line that is not a bullet is ignored, so headings and explanations stay
readable, but keep them in plain paragraphs: a bullet of prose would be
read as an ID.

[source,markdown]
----
# Import Exception List — Azure

The shared platform resources are owned by the platform team and
must stay out of workload repositories.

- /subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-shared-platform
- `/subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-shared-platform/providers/Microsoft.KeyVault/vaults/kvt-shared-001`
----

Each ID withholds that one resource only. Listing a resource group does
not withhold the resources inside it, which the scope lists under their
own IDs.

NOTE: Lists written as free text before the core parsed them are kept
as they were, and any ID not written as a bullet is ignored. Rewrite
such lists as bullets.

[#compliance-policy]
== Change a compliance policy

The compliance policies are Rego modules evaluated by Open Policy
Agent, not read by a model: `general/policies/compliance` on every
generate round, and `<provider>/policies/compliance` on the rounds whose
root module declares that provider. Kumoss ships one for `aws`,
`azurerm`, `google`, `kubernetes`, `oci`, and `vsphere`; give another
provider a policy by creating its prompt in Langfuse. Change a policy
like any other prompt, with the steps in <<change-a-prompt>>, but test
every version before you move the label: a broken version locks every
generate round it applies to (every round for the general policy, every
round of a module declaring the provider for a provider policy) until
the label is on a working one. To write, test, and publish a rule, see
xref:main:guides/write-a-policy-rule.adoc[Write a policy rule]; the
input and decision a policy works with, and the shipped rules, are in
xref:main:reference/compliance-policy.adoc[Compliance policy].

What a policy enforces is not restated in the guideline and resource
prompts. Those prompts feed both the IaC generator and the compliance
audit, so a ban written there would also be enforced by the model,
possibly differently from the policy. The shipped prompts keep positive
defaults (`allow_privilege_escalation = false`, S3 Block Public Access
fully enabled, outputs carrying secrets marked `sensitive = true`) and
leave the bans to Rego: they no longer tell the generator to avoid
`null_resource`, provisioners and `data "external"`, internet-open
ingress, basic roles or service account keys, `cluster-admin` or
`Allow any-user` grants, or `allow_unverified_ssl`. A round that
generates one of those is locked by a policy rather than written
correctly in the first place. If you add a rule to a policy, do not also
write it into a prompt; if you would rather the generator avoid a
pattern up front, phrase the prompt as the default to produce, not as a
prohibition.

[#troubleshooting]
== If something goes wrong

[#session-stops]
=== A session stops without an error

A `general/*` prompt has no version carrying your environment's label,
or does not exist. The run stops with `prompt_name=<name>. No version
labeled '<environment>'` in the core log, but the session shows no
failure: it keeps its last status (for example `filtering`), no
notification is sent, and the browser waits until its timeout. Set the
label on a version of that prompt; a new request can be sent right
away. This also happens after changing `environment` if prompts you
created by hand do not carry the new label: set it on every such prompt
before switching.

=== Conventions are missing from a session

A provider prompt that is deleted, or has no version with your
environment's label, is skipped without an error: that provider's
conventions silently disappear from every session. Restore the prompt
or its label.

=== A resource prompt is never used

Its name is not in `<provider>/guidelines/resources_list`, or does not
match the `<name>` part of the prompt exactly. See
<<add-a-resource-prompt>>.

[#checklist]
== Checklist for operators

* Review every shipped prompt before relying on a deployment: the
  naming conventions, security defaults, and compliance rules encode a
  policy, not yours.
* Write the prohibitions your organization needs as rules in the
  compliance policies: `<provider>/policies/compliance` for a
  provider's resources, `general/policies/compliance` for rules that
  span providers. No prompt lists forbidden actions any more; the
  shipped policies deny standalone deletions, removed customer-managed
  keys and command execution, and three critical misconfigurations per
  shipped provider (public ingress, admin grants and the like), nothing
  else. Review them before relying on them.
* Do not restate a policy rule in a prompt; see <<compliance-policy>>.
  Guidance the shipped prompts dropped along with those bans, and that
  no policy checks (no secrets in user data, Owner or User Access
  Administrator at narrower scopes, scoping other ingress to known
  CIDRs, tags or security groups, the alternatives to service account
  keys, credentials in the `vsphere` provider block, locking down the
  OCI default security list, OCI delete-protection defaults), is now
  checked by nothing: write it back into your own prompts, as a
  default, if you need it. `null_resource`, provisioners and
  `data "external"` are denied by the general policy's
  `command_execution` rule only when the compliance check is on; see
  xref:main:guides/deploy-to-production.adoc[Deploy to production].
* Decide who may edit prompts. Anyone who can edit prompts in the
  Langfuse project can change what the agents generate; give others a
  viewer role.
* Keep Langfuse reachable whenever the core starts; seeding is part of
  the boot.
* Back up `langfuse-db`; it holds your curated prompts.
