= Customize prompts
:description: Manage Kumoss's runtime prompt registry in Langfuse: seed files, naming, labels, composition, and how to add or change prompts safely.

Kumoss does not hard-code cloud knowledge. The instructions that tell
its agents how to name, configure, and secure resources are *prompts*
stored in the prompt management of https://langfuse.com/docs/prompt-management[Langfuse],
fetched by the core at request time. This guide explains the
three layers involved, the naming conventions, how seeding and runtime
lookup work, how the prompts are composed into a system prompt, and how
to add or change prompts safely.

Langfuse also collects Kumoss's traces. That is a separate function,
documented in xref:main:guides/monitor-with-langfuse.adoc[Monitor with
Langfuse], which also covers where Langfuse runs and how to log in.
Prompts curated in Phoenix, which Kumoss used before, are moved with
the script described in xref:main:guides/upgrade-notes.adoc[Upgrade
notes].

== Three different things, not one

[cols="1,2,2,3",options="header"]
|===
|Layer |Where |Who changes it |When it takes effect

|*Runtime prompts*
|Langfuse prompt management (*Prompts* in the Langfuse UI, on port 3000
in the default stack; persisted in `langfuse-db`)
|Prompt maintainers, in the Langfuse UI or API
|Immediately on the next request; the core caches nothing

|*Seed YAML files*
|`core/prompts/seed/<scope>/<type>/<name>.yaml` (`.rego` for policies)
in the repository
|Contributors and operators preparing a new deployment
|At core startup: missing prompts are created, and a changed seed is
published to the environments still on the previous seed (see
<<how-seeding-works>>)

|*Local Jinja layouts*
|`core/src/infrastructure/templates/base_layouts/` (`core/` and
`messages/`), inside the core image
|Kumoss developers
|After rebuilding the core image
|===

The seed files are the initial content of the registry, nothing more.
The Jinja layouts are the fixed skeletons of each agent's system prompt:
they define the agent's role, its tools and its output rules, and they
contain placeholders that the core fills with prompts fetched from
Langfuse. Operators customise the runtime prompts; the layouts are code.

== Seed file conventions

=== Path

[source]
----
core/prompts/seed/<scope>/<type>/<name>.yaml
core/prompts/seed/<scope>/policies/<name>.rego
----

* `<scope>` is `general` or a Terraform provider type name — the last
  segment of the provider's source address, such as `azurerm` for
  `hashicorp/azurerm` — matching `^[a-z0-9][a-z0-9_-]{0,63}$`. The
  shipped seeds use `general`, `aws`, `azurerm`, `google`, `oci`,
  `kubernetes` and `vsphere`; any other provider (`helm`, `datadog`...)
  can be given prompts by adding a folder with its type name.
* `<type>` is one of `guidelines`, `resources`, `compliance`, `policies`.
  Seeds of type `policies` are `.rego` files; every other type is a
  `.yaml` file.
* `<name>` must match `^[a-z0-9_]+$` (lowercase letters, digits,
  underscores).

The loader rejects any other depth, scope, type, or name at startup
with a `PromptSeedLoadError`, for example `Invalid prompt name
'Bad-Name' in ...; must match ^[a-z0-9_]+$`. That check only applies to
files it actually loads: the loader globs `*.yaml` and `*.rego` only,
so a `.yml` file, or any other extension, is silently skipped rather
than rejected — a typo in the extension produces no error at all, just
a missing prompt. A `.rego` file under a type other than `policies`, or
a `.yaml` file under `policies`, is rejected.

=== Qualified name

The Langfuse prompt name is derived from the path, never declared inside
the file, so a misfiled prompt cannot misreport its identity:

[source]
----
<scope>/<type>/<name>
----

Langfuse shows each `/` as a folder, so its *Prompts* view is laid out
like `core/prompts/seed/`: a folder per scope, and in it one per type.
A prompt you create by hand must carry the full name, slashes included,
to be found.

=== Content

[cols="1,1,1,4",options="header"]
|===
|Key |Required |Type |Meaning

|`body`
|yes
|non-empty string
|The prompt text, usually Markdown. Stored as a Langfuse *text* prompt.

|`description`
|no
|string
|The commit message of each version the seeder creates, shown in the
Langfuse version history.
|===

Every shipped seed provides both keys and starts with the repository's
SPDX comment header. The loader reads `body` and `description` and
ignores everything else in the mapping — an extra key is neither
rejected nor surfaced anywhere; it is dead weight in the file.

A `.rego` seed has no keys: the whole file, comments included, is the
body, so `opa fmt` and `opa test` run on the very file that is seeded.
It must not be empty. The commit message of its versions is generated
(`Rego policy evaluated by OPA (<name>).`).

[#how-seeding-works]
== How seeding works

A Langfuse prompt has numbered versions, and *labels* that each point
at one version at a time: setting a label on a version takes it off any
other. Langfuse keeps the `latest` label on the newest version itself.
Kumoss uses one label per `environment` value and one of its own,
`seed`.

At every core startup, after the database, Redis, and object storage
have been initialised, the seeder:

. Loads every seed file (sorted, validated as above).
. Makes an authenticated read against Langfuse at
  `telemetry.langfuse_url`, retrying for about 90 seconds while Langfuse
  does not answer. If it stays unreachable the boot fails with `Langfuse
  unreachable after 15 attempts`; if it rejects the key pair, with
  `Langfuse refused the API key pair (401)`. Langfuse must therefore be
  available whenever the core starts.
. For each seed, reads the prompt's version labelled `seed`, the one the
  seeder last pushed. A prompt without that label gets it on its latest
  version first; prompts migrated from Phoenix without it get it this
  way on the first boot.
. If the prompt does not exist, the seeder creates it as a text prompt
  whose first version carries every `environment` value as a label,
  `development`, `staging` and `production`, plus `seed`.
. If the text of the `seed` version differs from the seed file, the
  seeder creates a new version with the seed's text and moves to it,
  in one request, every environment label that is still on the `seed`
  version, together with `seed`. A label on any other version, or a
  label you removed, is left alone. If the latest version already holds
  the seed's text (you saved it by hand), the labels move to it instead
  of to a copy.
. Logs `Prompt seeding complete: N created, M updated, K unchanged`.

Only the text counts: the seeder compares the `seed` version's text
with the seed file, and ignores its config and commit message.

Consequences to plan for:

* *Seeding never moves a label off your versions.* A seed changed by a
  release reaches every environment label that is still on the `seed`
  version. Once you move a label to your own version, that label keeps
  it on every later boot, and seed changes for it are yours to merge by
  hand. Do not move `seed` onto your own version, and do not remove it:
  without it the seeder takes the latest version as its own, which may
  be yours.
* *New seed files are pushed too.* Adding a seed file and restarting the
  core creates the new prompt, even on an existing deployment.
* *A write fails whole.* A version is created together with its labels,
  and labels move in one request, so a failed write leaves the prompt as
  it was; boot fails with an error naming the prompt (and, for a label
  move, the version and labels), and the next boot tries again.
* *The environment label matters.* The core fetches prompts by name and
  label, and the label is `environment`. Seeded versions carry all three
  labels, so changing `environment` keeps working for them. It does not
  for prompts you created by hand, nor for labels you removed: the
  seeder never adds a label it did not find on its `seed` version. The
  next session then fails because, say, `general/guidelines/terraform`
  has no version labelled `production`. Set the new label on a version
  of every such prompt in Langfuse before switching.
* *Prompt versions are yours to manage.* Kumoss always fetches the
  version currently carrying the environment label. Publishing a new
  version and moving the label is how you roll a change out; moving the
  label back is how you roll it back.

== Runtime lookup

Each time an agent chain is rendered, the core fetches the prompts its
layout needs from Langfuse with the `<scope>/<type>/<name>` name and the
`environment` label, and reads the version's text: the text of a text
prompt, or the content of a chat prompt holding a single message (any
other shape is an error). The text is used as it is: Langfuse's
`+{{variable}}+` placeholders are not filled in. There is no cache: every
session sees the version the label is on now, so editing a prompt in
Langfuse takes effect on the next run without rebuilding or restarting
the core.

Which provider prompts a session uses depends on its root module: the
core asks for the `<provider>/*` prompts of every provider the module's
`required_providers` declares. A provider prompt that does not exist is
simply left out, so a provider without prompts — `random`, `helm`, or a
module that declares no provider yet — gets the `general/*` prompts
only. When a module uses several providers that have the same
guideline (for example `azurerm` and `kubernetes` both have
`permissions`), the agent receives all of them, each as a
section headed by its provider name. A resource template the
compositor picks is taken from the first provider that has it.

If a requested `general/*` prompt (or a version with the right label)
does not exist, the fetch fails with `prompt_name=<name>. No version
labelled '<environment>'` and the background run stops. This error is not one the runner converts into a failed
round: the session keeps its last status (for example `filtering`), no
failure message or notification is produced, and the browser's event
stream stays open until its timeout. The workspace is cleaned up and the
session's in-flight guard is released, so a new request can be sent once
the prompt exists. There is no fallback to seed files at runtime.

[#guideline-prompts]
=== Which guideline prompts are read, and when

For each provider of the session's root module the core reads these
guideline prompts when it has them; a missing one is skipped, not an
error:

[cols="2,3",options="header"]
|===
|Requested by |Prompt

|Prompt compositor (every generate and drift round)
|`<provider>/guidelines/abbreviations`,
`<provider>/guidelines/resources_list`

|IaC generator and compliance checker
|`<provider>/guidelines/resource_creation`,
`<provider>/guidelines/networking`, `<provider>/guidelines/permissions`

|Drift exception filter (every drift round and every generate round's
drift pre-check)
|`<provider>/guidelines/drift_exceptions`

|Import scope diff (every import round that finds unmanaged resources)
|`<provider>/guidelines/import_exceptions`
|===

Because a missing provider prompt is skipped, deleting one in Langfuse
does not break sessions — it silently removes that provider's
conventions from them. The `general/*` prompts are the opposite: they
are read for every session and a missing one aborts the run with
`No version labelled ...`.

The import exception list is only read once the scope listing has
returned resources that the state does not track. Only `azurerm`,
`google` and `aws` scopes can be listed, so `kubernetes` and `vsphere`
ship without one.

Keep this in mind when you delete a prompt in Langfuse or trim the seed
set for a deployment.

NOTE: Prompt scopes were renamed from the core's former provider names
to Terraform provider type names: `azure-*` is now `azurerm-*`, `gcp-*`
is `google-*` and `vmware-*` is `vsphere-*`. The seeder creates the new
names on the next boot from the seed files, but versions you curated
under the old names stay where they are and are no longer read; copy
them to the new names. See xref:main:guides/upgrade-notes.adoc[Upgrade
notes].

[#drift-exception-rules]
== Drift exception rules

`<provider>/guidelines/drift_exceptions` is the list of things drift
remediation must never touch. It is read by a dedicated *drift exception
filter*: after the task splitter turns a drift report into operations,
and after the reconciliation filter has removed the session's own
changes, this agent receives the remaining operations together with the
rules and returns the ones no rule covers. Only those are remediated.
Whatever it removes is logged as a warning and reported in the drift
report's `whitelisted_exceptions` block, one entry per excluded change,
naming the change and the rule that covers it. That block is kept apart
from `unreconciled_drift`, which is for drift the round genuinely failed
to fix, and it does not lower the report's outcome: leaving an excluded
change alone is the intended result.

The filter runs on *every* drift round, full or partial, and on the
drift pre-check inside every generate round, so a generate round cannot
silently "fix" an excluded resource either. With several providers in
the root module, the filter receives the rules of each of them.

This is not the same brake as `general/guidelines/targeting_policies`.
Targeting policies decide which resources a *partial* drift round plans
at all; they never reach a full drift round and they never see the
operations. Exception rules apply to the operations of every drift
round, whatever produced them.

=== How to write one

The body is prose, read by a model. Keep each exception on its own
bullet, and name the resource address, type, attribute, tag, namespace
or naming pattern precisely enough that an agent can match it against a
sentence like "In `main.tf`, for `azurerm_key_vault.kvt_001`: update the
tag `owner` from `platform` to `payments`." Say what must not be
reconciled, and why — the reason is what the agent quotes back in the
report.

The shipped seed has three sections, and they are the rule kinds the
filter understands:

* *Provider quirks*: a permanent false diff the provider reports on every
  plan.
* *Resources managed outside Terraform*: something another system owns
  and keeps changing on purpose.
* *Environment, team and naming carve-outs*: whole slices of the estate a
  workload session must not touch.

The agent may also *trim* an operation: when one instruction bundles an
excluded change with a legitimate one, it keeps the legitimate part and
drops the rest. Rules that name a single attribute are therefore as
useful as rules that name a whole resource.

=== Worked examples

[source,yaml]
----
  ## Provider quirks (permanent false diffs)
  - The `azurerm` provider always reports a diff on the `created_at` tag
    written by the tagging policy; never reconcile that tag.

  ## Resources managed outside Terraform
  - The values of `azurerm_key_vault_secret` are rotated by the secrets
    platform; never reconcile them.

  ## Environment, team and naming carve-outs
  - Never reconcile resources in the `rg-shared-platform` resource
    group; the platform team owns them.
----

With those rules in place, a drift round that found "Delete resource
`azurerm_storage_account.sta_shared_001` in `rg-shared-platform`"
remediates nothing, stops rather than re-planning, and lists the resource
under `whitelisted_exceptions` in the report, quoting the carve-out — with
the outcome still `Succeeded`, because nothing was left unreconciled
involuntarily.

[#import-exception-list]
== Import exception list

`<provider>/guidelines/import_exceptions` names the resources an import
round must never bring under Terraform, even when they exist in the
cloud scope and the state does not track them. Unlike every other
prompt, it is not written for a model. The core parses the body itself
and removes the listed IDs from the scope diff before anything else
sees it:

* The list applies on *every* import round, full scope or partial. A
  withheld resource never reaches the `import_filter` selection agent,
  the IaC generator, or `terraform import`, so neither a broad request
  nor a model's selection can bring it back.
* The comparison follows the same rule as the diff against the state.
  Azure ARM IDs match case-insensitively, so
  `/subscriptions/.../resourceGroups/rg-a` also withholds a scope entry
  spelled `/resourcegroups/RG-A`. GCP and AWS IDs match exactly, because
  two of their resources can differ only by case.
* What was withheld is not an error. The import report receives it as
  `excluded_resource_ids` and names each one as skipped on purpose. When
  every unmanaged resource in the scope is withheld, the round ends with
  `Every unmanaged resource in the scope <scope> is on the import
  exception list.` and an empty report.
* An ID on the list that is not in the scope, or is already managed,
  has no effect and is not reported.

This is not the same brake as
<<drift-exception-rules,`drift_exceptions`>>. Drift exception rules are
prose that an agent matches against drift operations. The import
exception list is a list of exact IDs, enforced in code.

=== How to write one

Put each resource ID on its own Markdown bullet (`-` or `*`), exactly
as the cloud's scope listing returns it: the full ARM ID for Azure, the
asset name without the `//service.googleapis.com/` prefix for GCP (for
project IAM, the space-separated `<project-id> <role> <member>` entry),
and the ARN for AWS. See
xref:main:reference/api/iac.adoc[IaC sidecar API] for the exact shapes.
Backticks around the ID are optional. Every line that is not a bullet
is ignored, so headings and explanations stay readable in Langfuse, but
keep them in plain paragraphs: a bullet of prose would be read as an ID.

[source,yaml]
----
body: |
  # Import Exception List — Azure

  The shared platform resources are owned by the platform team and
  must stay out of workload repositories.

  - /subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-shared-platform
  - `/subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-shared-platform/providers/Microsoft.KeyVault/vaults/kvt-shared-001`
----

Each ID withholds that one resource only. Listing a resource group does
not withhold the resources inside it, which appear in the scope listing
under their own IDs.

NOTE: Before this list was parsed by the core, the `import_filter`
agent read it as prose. Seeding never overwrites your versions, so a
deployment whose list was curated in free text keeps that text: any ID
not written as a bullet is now silently ignored. Rewrite such lists as
bullets.

[#compliance-policy]
== Compliance policy

The compliance policies are Rego v1 modules, seeded from
`core/prompts/seed/<scope>/policies/compliance.rego`:

* `general/policies/compliance`, `package kumoss.compliance`, runs on
  every generate round and must exist;
* `<provider>/policies/compliance`, `package
  kumoss.providers.<provider>`, runs on the rounds whose root module
  declares that provider. A provider without one, such as `random`, is
  skipped. Kumoss ships one for `aws`, `azurerm`, `google`,
  `kubernetes`, `oci` and `vsphere`; give another provider a policy by
  creating its prompt in Langfuse.

They are not read by a model: when
`orchestration.enable_compliance_checker` is `true`, the core runs the
general policy and those of the session's providers together, in one
evaluation with the `opa` binary, against the final plan of every
generate round, before the LLM compliance audit, and merges both
results into one compliance report. A deny, or a policy that cannot be
evaluated, locks the session. The input, the decision a policy must
return, the shipped rules and the failure semantics are in
xref:main:reference/compliance-policy.adoc[Compliance policy].

What a policy enforces is not restated in the guideline and resource
prompts. Those prompts feed both the IaC generator and the LLM
compliance audit, so a ban written there would also be enforced by the
model, possibly differently from the policy. The shipped prompts keep
positive defaults (`allow_privilege_escalation = false`, S3 Block
Public Access fully enabled, outputs carrying secrets marked
`sensitive = true`) and leave the bans to Rego: they no longer tell
the generator to avoid `null_resource`, provisioners and
`data "external"`, internet-open ingress, basic roles or service
account keys, `cluster-admin` or `Allow any-user` grants, or
`allow_unverified_ssl`. A round that generates one of those is locked
by the policy rather than written correctly in the first place. If you
add a rule to a policy, do not also write it into a prompt; if you
would rather the generator avoid a pattern up front, phrase the prompt
as the default to produce, not as a prohibition.

Like every other prompt, each policy is a Langfuse text prompt, fetched
on each evaluation from the version carrying the `environment` label,
and seeded the same way: a release that changes a seed moves only the
labels still on the `seed` version, and a policy you customized is
kept. The core reads the raw text of the version: Langfuse's
`+{{variable}}+` templating is not applied, so the braces of Rego are
safe.

=== Changing the policy

. In Langfuse, open the policy (`general/policies/compliance` or
  `<provider>/policies/compliance`) under *Prompts* and create a new
  version with the edited Rego. Do not set the environment
  label on it yet.
. Test that version first (below).
. Set the environment label on it. The next generate round of that
  environment runs it; moving the label back to the previous version is
  the rollback.

One version serves *every* generate session of the environment that
the policy applies to: every session for the general policy, every
session whose module declares the provider for a provider policy. A
syntax error, a wrong type in the decision or a rule that errors does
not skip the policy: it blocks each of those rounds with
`policy_unavailable` until the label is on a working version. The
startup check catches a broken general policy, or a broken policy of a
provider that ships a seed, only when the core restarts.

=== Testing a version before labelling it

Copy the version's text from Langfuse into a file, for example
`aws.rego`, and run OPA 1.22.4, the version in the core image, on it
together with the other policies a round would run (here the general
policy in `general.rego`):

[source,bash]
----
opa check general.rego aws.rego
opa test general.rego aws.rego my_tests/
opa eval --stdin-input --strict-builtin-errors -d general.rego \
  -d aws.rego data.kumoss < input.json
----

`input.json` is a document as described in
xref:main:reference/compliance-policy.adoc#input[the input reference],
for example a plan's `terraform show -json` wrapped in `{"plan": ...,
"kumoss": ...}`. The tests in `core/tests/policies` show how to write
`opa test` cases against the shipped rules.

== How prompts are composed into a system prompt

For a generate or drift round the core builds the conventions in two
model passes and then renders the layouts:

. *First compositor pass.* The `prompt_compositor` layout is rendered
  with the `resources_list` (as the list of available templates) and
  `abbreviations` (as the list of available abbreviations) of every
  provider of the root module that has them. The small model reads the user's request and calls
  the `construct_information` tool with the resource template names and
  abbreviations it considers relevant. Names must match the
  `resources_list` entries exactly.
. *Second compositor pass.* The layout is rendered again, this time
  including the full text of the resource prompts selected in the
  first pass. The model looks for dependencies (a subnet needs a
  network, a function needs a storage account, and so on) and returns
  additional templates and abbreviations. Both passes are merged into
  the round's conventions.
. *Rendering the agent layouts.* The IaC generator layout (and the
  compliance checker layout) receives `general/guidelines/terraform`,
  each provider's `resource_creation`, `networking`, and `permissions`
  guidelines, and a concrete-implementation section built from the selected
  `<provider>/resources/*` prompts and abbreviations. The compliance
  checker additionally receives `general/compliance/report`; the
  report generator receives `general/compliance/impact` for generate
  reports; the drift target generator receives
  `general/guidelines/targeting_policies`; the drift exception filter
  receives each provider's `drift_exceptions`; the request filter
  receives `general/guidelines/requests`.

The layouts also carry fixed content that is not in Langfuse: the
agent's role, the tools it may call, output format rules, and the
working directory. Those change only with a core rebuild.

`<provider>/guidelines/import_exceptions` is the one prompt that is never
rendered into a layout: the core reads the IDs out of it, and the
`import_filter` layout only receives what is left after they are
removed.

*Discovery depends on `resources_list`.* Nothing enumerates the
`<provider>/resources/*` prompts that exist in Langfuse. The compositor
can only pick names that appear in `resources_list`, and every name it
picks is then fetched from the module's providers in order; a name
listed there without a matching resource prompt is logged as a warning
and its conventions are missing from the round. The reverse is just as
important: a resource prompt that exists but is not named in its
provider's `resources_list` is never selected — the compositor has no other way to
discover it, and the loader does no cross-check between the seed files
on disk and the `resources_list` catalogue at startup. Whenever you add
a resource seed, add its name to `resources_list` in the same change,
for every provider you edit. The Azure `resources_list` now names all 16
shipped Azure resource seeds; keep it that way as you add more.

== Examples

All examples are fictitious and use the repository conventions.

=== A provider-wide guideline seed

File `core/prompts/seed/aws/guidelines/networking.yaml` (shipped; body
shortened here for space — see the file for the full text), producing the
Langfuse prompt `aws/guidelines/networking`:

[source,yaml]
----
# SPDX-FileCopyrightText: 2026 INDUSTRIA DE DISEÑO TEXTIL S.A. (INDITEX S.A.)
#
# SPDX-License-Identifier: Apache-2.0

description: AWS networking conventions (VPCs, subnets, gateways, security groups).
body: |
  # AWS Networking Guidelines

  ## Topology
  - Default to a multi-AZ VPC with public and private subnets per
    availability zone.
  - For multi-environment deployments, use separate VPCs per
    environment (`dev`, `staging`, `prod`) connected through Transit
    Gateway or VPC peering.

  ## Address space
  - Use RFC1918 ranges. Avoid overlapping with on-premises CIDRs
    or other VPCs that will be peered.
  - Allocate `/16` per VPC by default; carve `/24` subnets within.
  - Spread subnets across at least two availability zones.
----

=== A resource (component) seed

File `core/prompts/seed/aws/resources/s3_bucket.yaml` (shipped; body
shortened here for space — see the file for the full text), producing
`aws/resources/s3_bucket`:

[source,yaml]
----
# SPDX-FileCopyrightText: 2026 INDUSTRIA DE DISEÑO TEXTIL S.A. (INDITEX S.A.)
#
# SPDX-License-Identifier: Apache-2.0

description: AWS S3 Bucket default configuration (encryption, versioning, public access, lifecycle, logging).
body: |
  # AWS S3 Bucket

  For an S3 Bucket, unless explicitly requested otherwise, use the
  following default configuration:

  - Naming convention: `<project>-<purpose>-<environment>`. Bucket
    names are globally unique, lowercase, 3-63 characters.
  - Versioning must be enabled.
  - Server-side encryption must use aws:kms with bucket key enabled.
  - Block Public Access must be fully enabled unless the request
    explicitly requires a public bucket.
----

=== The matching `resources_list` entry

The compositor can only select `s3_bucket` because it appears in
`core/prompts/seed/aws/guidelines/resources_list.yaml`
(`aws/guidelines/resources_list`). The shipped file is a bulleted
catalogue; a new resource prompt needs one more line in the same style,
for example a hypothetical `sqs_queue` resource that does not ship
today:

[source,yaml]
----
description: Names of aws/resources/* prompts the compositor may select from.
body: |
  # Available AWS Resource Templates

  ...
  - `s3_bucket` — S3 bucket with encryption, versioning, and public access block.
  - `sqs_queue` — SQS queue with encryption, dead-letter queue, and retention.
  ...
----

The name in backticks must equal the `<name>` part of the resource
prompt exactly, and it must exist on both sides: a resource prompt with
no `resources_list` entry is never selected, and a `resources_list`
entry with no matching resource prompt contributes nothing when picked.

*List style is not uniform across providers.* AWS, Azure, GCP, OCI, and
vSphere name entries in backticks with a trailing description, as above;
the Kubernetes `resources_list` uses plain bullets with no backticks at all
(`- namespace`, `- deployment`, and so on). There is no enforced format
— the compositor only needs the bare name to appear somewhere in the
body. When you edit a `resources_list`, follow the style already used
in that specific file rather than copying another cloud's convention.

=== Adding a new component prompt to a fresh deployment

. Create `core/prompts/seed/<provider>/resources/<name>.yaml` with
  `description` and `body`.
. Add the `<name>` entry to
  `core/prompts/seed/<provider>/guidelines/resources_list.yaml`.
. Rebuild the core image (`docker compose build core`) so the new seed
  files are inside it, and start the stack. The seeder creates
  `<provider>/resources/<name>` and the catalogue from the updated
  `resources_list`.

=== Adding or changing a prompt on an already running deployment

Without a core rebuild, edit the prompts in Langfuse:

. Open Langfuse (`\http://localhost:3000` in the default stack) and go
  to *Prompts*.
. For a new component: either add the seed file, rebuild and restart the
  core (new names are created), or create the *text* prompt
  `<provider>/resources/<name>` directly in Langfuse. In both cases the
  new version must carry the deployment's `environment` label
  (`development` by default); the seeder labels what it creates with all
  three environments, a manual creation must be labelled by hand.
. Open `<provider>/guidelines/resources_list`, create a new version with
  the extra line, and set the environment label on it.
. Run a session that mentions the new resource. No core rebuild or
  restart is needed for step 3 to take effect.

To *change* an existing prompt (a naming rule, a security default, a
compliance rule), create a new version in Langfuse and set the
environment label on it. Keep the previous version; moving the label
back is the rollback. When the Langfuse UI offers to set the
`production` label on a new version, that is the label a `production`
deployment reads: leave it unticked to try the version out under
`development` or `staging` first.

== Checklist for operators

* Review every shipped prompt before relying on a deployment: naming
  conventions, security defaults, and compliance rules encode a policy,
  not yours.
* Write the prohibitions your organization needs as Rego rules in the
  compliance policies: `<provider>/policies/compliance` for a
  provider's resources, `general/policies/compliance` for rules that
  span providers. No prompt lists forbidden actions any more; the
  shipped policies deny standalone deletions, removed customer-managed
  keys and command execution, and three critical misconfigurations per
  shipped provider (public ingress, admin grants and the like), nothing
  else. Review them before relying on them.
* Keep Langfuse reachable during core startups; seeding is part of the
  boot.
* Do not restate a policy rule in a prompt; see <<compliance-policy>>.
  Guidance the shipped prompts dropped along with those bans, and that
  no policy checks (no secrets in user data, Owner or User Access
  Administrator at narrower scopes, scoping other ingress to known
  CIDRs, tags or security groups, the alternatives to service account
  keys, credentials in the `vsphere` provider block, locking down the
  OCI default security list, OCI delete-protection defaults), is now
  checked by nothing: write it back into your own prompts, as a
  default, if you need it. `null_resource`, provisioners and
  `data "external"` are denied by the general policy's
  `command_execution` rule only when the compliance check is on, see
  xref:main:guides/deploy-to-production.adoc[Deploy to production].
* Decide who may edit prompts. Anyone with a role that can edit prompts
  in the Langfuse project can change what the agents generate; give
  others a viewer role.
* Treat the `environment` value as part of the prompt data model: it is
  the label every fetch uses.
* Back up `langfuse-db`; it holds your curated prompts. Traces are in
  ClickHouse.
