= Development
:description: Contribute to Kumoss: prerequisites, running the stack for development, core and frontend tests, linting, and updating sidecar clients.

This guide covers contributing to Kumoss itself — running the repository's
own test suites, checks, and tooling. It does not cover deploying or
operating Kumoss; for that, see xref:main:quickstart.adoc[] and
xref:main:guides/deploy-to-production.adoc[].

== Prerequisites

Before contributing, read xref:main:contributing.adoc[] for the
Contributor License Agreement, the code of conduct, and the process for
proposing a change.

== Repository layout

The repository is a monorepo: the Rust core (axum, tokio, sqlx,
MiniJinja) in `core/`, the Python (FastAPI) IaC, notifications and LLM
sidecar services in `services/`, the React web application in
`client/web/`, and the sidecar OpenAPI contracts in `contracts/`. See
xref:main:architecture.adoc[] for how they fit together.

== Running the stack for development

Copy each `env.sample` to a `.env` next to it (`core/.env` and
`services/llm/.env` are required), set the two model strings in `config.yaml`, and run `docker
compose up --build`. xref:main:quickstart.adoc[] is the step-by-step
guide. `--build` matters: without it, Compose runs the published
release images (`ghcr.io/inditextech/kumoss-*`) instead of your
checkout. A `docker compose pull` later replaces locally built images
with the published ones again.

After a code change, rebuild and recreate the affected service, for
example `docker compose up -d --build core`. An edit to `config.yaml`
needs only `docker compose restart core`, because Compose bind-mounts
that file; restart `llm` too when you change the `llm` or `web_search`
sections, which the LLM sidecar reads from the same file.

[#local-compose-overrides]
=== Local Compose overrides

Settings that belong to your machine rather than to the project go in
`docker-compose.override.yml`, which Compose loads automatically and
git ignores. `docker-compose.override.example.yml` is the tracked
template — copy it rather than editing it in place:

[source,bash]
----
cp docker-compose.override.example.yml docker-compose.override.yml
----

[#tls-inspecting-proxy]
=== Behind a TLS-inspecting proxy

On a corporate network that inspects HTTPS, most outbound container
requests fail while a few domains keep working: `web_search` returns
engine snippets instead of page content, and `docker compose logs llm`
shows the reads failing before any HTTP request is sent.

[source,text]
----
Page read for '<url>' failed, falling back to the engine snippet:
PageReadError("could not render '<url>'")
(RuntimeError('[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify
failed: self-signed certificate in certificate chain'))
----

The proxy terminates TLS and re-signs it with its own root, which the
containers do not trust; the domains that still work are the ones the
proxy passes through untouched. Confirm it by looking at who signed what
you received:

[source,bash]
----
docker compose exec llm sh -c \
  'echo | openssl s_client -connect example.com:443 \
   -servername example.com 2>/dev/null | openssl x509 -noout -issuer'
----

An `issuer` naming your company rather than a public CA confirms the
interception. The fix is two-part, both wired in the override template
above, and keeps the certificates on your machine:

* *Build* — the llm image downloads Chromium, and every image fetches its
  dependencies over HTTPS, so the roots are needed at build time too. The override points the `host-certs` build context at the host
  directory holding them.
* *Runtime* — the override mounts that directory at `KUMOSS_CA_DIR`, and
  each entrypoint merges its certificates into a bundle and points the
  HTTP clients at it before starting the server.

A *hostname mismatch* is not a trust problem: the proxy is sinkholing
that domain under its filtering policy, and the certificate honestly
belongs to the sinkhole. No configuration fixes that one.

[#core-tests]
== Core tests

The core is a Cargo project (`core/Cargo.toml`, Rust edition 2024). Its
checks are formatting, Clippy with warnings denied, and the test suite —
unit tests next to the code in `core/src/` and integration tests in
`core/tests/`:

[source,bash]
----
cd core
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
----

The integration tests (`core/tests/schema_parity.rs`,
`core/tests/api_catalog.rs`) need a PostgreSQL they may freely write
to, named by `KUMOSS_TEST_DATABASE_URL`; when the variable is unset they
print a skip notice and pass. Point it at a *disposable* database, never
at the compose stack's `core-db`.

To run everything without a local Rust toolchain, use the same image as
the build stage of `core/Dockerfile` and a throwaway PostgreSQL:

[source,bash]
----
docker network create kumoss-test
docker run -d --rm --name kumoss-test-db --network kumoss-test \
  -e POSTGRES_USER=kumoss -e POSTGRES_PASSWORD=kumoss \
  -e POSTGRES_DB=kumoss_test postgres:17
docker run --rm --network kumoss-test -v "$PWD/core":/app -w /app \
  -e KUMOSS_TEST_DATABASE_URL=postgres://kumoss:kumoss@kumoss-test-db:5432/kumoss_test \
  rust:1-bookworm sh -c 'rustup component add rustfmt clippy &&
    cargo fmt --check &&
    cargo clippy --locked --all-targets -- -D warnings &&
    cargo test --locked'
docker rm -f kumoss-test-db && docker network rm kumoss-test
----

The build output lands in `core/target/`, which git ignores.

== Frontend checks

Node 24:

[source,bash]
----
cd client/web
npm ci
npm run lint
npm run test:ci
npm run build
----

== Sidecar tests

Each sidecar service has its own `tooling` dependency group with
`pytest` and its test helpers (the exact set differs per service):

[source,bash]
----
cd services/<name>
uv sync --group tooling
uv run pytest
----

== Linting and formatting

`pre-commit run --all-files` runs Ruff (`ruff check` and `ruff format`)
over the Python sidecars, the REUSE check, and gitleaks secret scanning.
The core's Rust formatting and lints are `cargo fmt` and `cargo clippy`
(see <<core-tests>>). Install the hooks once
with `pre-commit install`.

== Continuous integration

Pull requests run Repolinter, the REUSE compliance check, the
Conventional Commits check, and an offline Markdown link and anchor
check, plus a Verify workflow: frontend type check, tests, and
production build; the core's `cargo fmt --check`, Clippy and `cargo
test`, with the integration tests against a disposable PostgreSQL 17
service; and the pytest suite of each sidecar service.

[#regenerating-clients]
== Updating sidecar clients

Changing a sidecar's behavior means updating its spec in
`contracts/openapi/`, its conformance suite in `contracts/conformance/`
(the `llm` contract has none), and the core's client for that service.
The core's clients are hand-written Rust — nothing is generated:

* `core/src/infrastructure/external/` — authz, mapping and notifications,
  plus the shared bearer-auth, timeout and RFC 7807 handling;
* `core/src/infrastructure/terraform/iac.rs` — IaC;
* `core/src/infrastructure/llm/sidecar.rs` — LLM.

After changing a spec, update the matching client and its tests in
`core/` so requests, responses and error handling still follow the
document, then run the core checks above.
