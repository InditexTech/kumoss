= Authorization sidecar API
:description: OpenID AuthZEN 1.0 Access Evaluation for organizational access control. Kumoss consults the PDP on every IaC and PR write route.

The authorization service answers *may this user perform this action on
this scope?* — asked before every IaC generation, drift detection,
import, apply, PR creation, and PR merge.

Contract: `contracts/openapi/authz.v1.yaml`, implementing the OpenID
AuthZEN 1.0 Access Evaluation API (§5). Kumoss bundles no PDP
implementation: authorization is an optional extension point you deploy
yourself and point `services.authz.endpoint` at. Bearer token: the
value of the variable named by `services.authz.token_env`,
`KUMOSS_AUTHZ_TOKEN` by default. The service is *optional* and ships
disabled (`services.authz.enabled: false`, `endpoint: ""`).

[IMPORTANT]
====
*Kumoss's own roles do not live here.* The operation roles (`developer`
< `devops`) and panel roles (`viewer` < `editor` < `admin`) that decide
what a signed-in user can do are rows in the core database, managed
from the admin panel. The AuthZEN PDP is an *organizational* gate — it
lets you enforce policies like "only the platform team may generate
infrastructure in the production subscription." See
xref:main:reference/roles-and-permissions.adoc[Roles and permissions].
====

== Endpoints

The contract exposes two endpoints:

[cols="3,4",options="header"]
|===
|Endpoint |What it does

|`POST /access/v1/evaluation`
|Evaluates whether a subject is permitted to perform an action on a
resource, per AuthZEN §5. *Called on every write route.*

|`GET /healthz`
|Liveness probe, answers `\{"status":"ok"}`.
|===

== Enforcement

The core calls the PDP on every route that mutates infrastructure or
repository state. The `action.name` value maps to the operation:

[cols="3,2,4",options="header"]
|===
|Core route |action.name |When

|`POST /v1/iac/generate`
|`generate`
|First call and iterations

|`POST /v1/iac/drift`
|`drift`
|First call and iterations

|`POST /v1/iac/import`
|`import`
|First call and iterations

|`POST /v1/iac/apply`
|`apply`
|Apply trigger
|===

NOTE: PR routes (`PUT /repository/pr` and `PUT /repository/pr/merge`) are
governed by Kumoss's own operation roles, not by the authz PDP. See
xref:main:reference/roles-and-permissions.adoc[Roles and permissions].

When `services.authz.enabled` is `false` (the default), the core does
not call out at all and treats every operation as authorized. When
enabled, the core *never* fails open:

[cols="2,4",options="header"]
|===
|Situation |What the core answers

|PDP unreachable, or the call times out
|`504` (gateway timeout)

|PDP returns a network-level error
|`502` (bad gateway)

|PDP returns `decision: false`
|`403` with the PDP's `reason_user` context

|PDP returns `decision: true`
|The request proceeds
|===

== POST /access/v1/evaluation

=== Request

[source,json]
----
{
  "subject": {
    "type": "user",
    "id": "https://login.microsoftonline.com/.../v2.0",
    "properties": {
      "issuer": "https://login.microsoftonline.com/.../v2.0",
      "email": "someone@example.com",
      "groups": ["platform-team", "devops"]
    }
  },
  "action": {
    "name": "generate"
  },
  "resource": {
    "type": "scope",
    "id": "my-subscription-id",
    "properties": {
      "provider": "azure",
      "repo_uri": "https://dev.azure.com/org/project/_git/infra",
      "iac_path": "environments/dev"
    }
  }
}
----

==== Subject

[cols="2,1,4",options="header"]
|===
|Field |Required |Description

|`type`
|Yes
|Always `user`.

|`id`
|Yes
|The OIDC `iss` (issuer) claim from the user's token.

|`properties.issuer`
|No
|The OIDC `iss` claim (universal default).

|`properties.email`
|No
|Present only when the token's `email_verified` is true (universal default).

|`properties.*`
|No
|Any additional claims configured via `oidc.claims` in `config.yaml`.
For example, `groups`, `identifier`, `tenant_id`. See
xref:main:reference/configuration.adoc#config-oidc[OIDC configuration].
|===

==== Action

[cols="2,1,4",options="header"]
|===
|Field |Required |Description

|`name`
|Yes
|One of: `generate`, `drift`, `import`, `apply`.
|===

==== Resource

[cols="2,1,4",options="header"]
|===
|Field |Required |Description

|`type`
|Yes
|Always `scope`.

|`id`
|Yes
|The scope identifier (subscription, project, account).

|`properties.provider`
|No
|`azure`, `gcp`, `aws`, `oci`, `kubernetes`, or `vmware`.

|`properties.repo_uri`
|No
|The git repository URL.

|`properties.iac_path`
|No
|The IaC path within the repository. Omitted when empty.
|===

`additionalProperties` is `false` on the request envelope, subject,
action, and resource objects. It is `true` on all `properties` objects,
so PDPs may read custom fields.

=== Response

[source,json]
----
{
  "decision": true,
  "context": {
    "reason_user": {
      "en": "Authorized by platform policy."
    },
    "reason_admin": {
      "en": "Policy platform-team-azure matched."
    }
  }
}
----

[cols="2,4",options="header"]
|===
|Field |Meaning

|`decision`
|Required boolean. `true` to allow, `false` to deny.

|`context.reason_user`
|Optional. Human-readable explanation shown to the end user on denial.

|`context.reason_admin`
|Optional. Detailed explanation logged at WARNING for operators.
|===

A denial is still `200`: the decision was computed, and it was "no."
The error statuses are for cases where no decision could be reached.

=== Error responses

Error bodies use `application/problem+json` per RFC 9457.

[cols="1,5",options="header"]
|===
|Status |Meaning

|`200`
|A decision was computed, granted or denied.

|`400`
|Malformed request (bad JSON, non-UTF-8).

|`401`
|Missing or invalid bearer token. Carries a `WWW-Authenticate: Bearer`
challenge.

|`422`
|Well-formed JSON that failed schema validation.

|`502`
|Downstream backend error inside the PDP.
|===

== Stub PDP

A minimal always-allow (or always-deny) stub is included for testing
the conformance suite and local development:

[source,bash]
----
cd contracts/conformance/authz
uv sync
STUB_DECISION=true uv run uvicorn stub:app --port 8083
----

Set `STUB_TOKEN=mysecret` to require bearer auth on the stub. Set
`STUB_DECISION=false` to make it deny everything.

[#conformance]
== Conformance

The implementation-agnostic Schemathesis suite at
`contracts/conformance/authz/` runs against any implementation of this
contract:

[source,bash]
----
cd contracts/conformance/authz
uv sync
uv run pytest \
  --service-url=https://authz.your.example \
  --service-token=$YOUR_TOKEN
----

`--service-token` is needed only if the implementation enforces
authentication.

The suite checks schema conformance of the responses — that valid
requests produce documented status codes with documented shapes. It
cannot check that the decisions are *correct*: a PDP that grants
everything passes it. Correctness of the policy is your own test
suite's job.
