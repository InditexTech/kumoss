= Mapping sidecar API
:description: The contract that turns a business identifier into the repository to clone. Kumoss bundles a prefix-based implementation, enabled by default, that resolves a bare repository name under a configured URL prefix.

The mapping service answers one question: *given what my organization
calls this thing, which repository holds its IaC?* The identifier can
be a project name, a subscription code, a product slug, or a full git
URL — whatever the organization already uses. The service returns the
clone URL.

Contract 2.0.0 dropped the former best-effort `terraform_provider` and
`scope_id` fields and the `TerraformProvider` enum: the providers and
scopes of a session come from its root module and its
xref:main:reference/root-module-manifest.adoc[manifest] rather than
from a lookup, so nothing consumed them. A request that still sends
`terraform_provider` fails validation with `422`.

The core calls the service when the web wizard scans a repository: what
the user types in the repository step goes to
`POST /api/v1/repository/parse`, which resolves it here before cloning,
and every later call of the session uses the resolved `repo_url`. It
calls the service once more when a session's first `generate`, `drift`
or `import` call carries a `project_identifier` (what the user typed,
echoed by the parse route), to check that it still resolves to that
call's `repo_uri` before any session is created. The core's former
`POST /api/v1/mapping/resolve` passthrough was removed together with
the provider and scope fields.

Contract: `contracts/openapi/mapping.v1.yaml`, version 2.0.0. Kumoss
bundles a reference implementation in `services/mapping`, *enabled by
default* (`services.mapping.enabled: true`, `endpoint:
"http://mapping:8081"`); point `services.mapping.endpoint` at your own
implementation to replace it. Bearer token: the value of the variable
named by `services.mapping.token_env`, `KUMOSS_MAPPING_TOKEN` by
default.

It is internal-only: only the core calls it, never the browser.

[#bundled]
== The bundled implementation

The bundled service resolves an identifier in one of two ways:

* An `https://` URL passes through unchanged.
* A bare repository name — letters, digits, `.`, `_` and `-`, no
  slashes — is appended to `MAPPING_PREFIX_IDENTIFIER` with a `.git`
  suffix (not doubled when the name already ends in `.git`). With
  `MAPPING_PREFIX_IDENTIFIER=https://github.com/MySuperOrg/`, `foo`
  resolves to `\https://github.com/MySuperOrg/foo.git`.

Anything else, or a bare name while the prefix is empty, is `404` with
a problem document that says why; the wizard shows that reason. Set the
prefix in `services/mapping/.env` (Compose) or `mapping.env` (Helm). It
must be an `https://` URL with a host and no password, query or
fragment, and a trailing `/` is added if missing; the service refuses
to start otherwise. Leave it empty to accept full URLs only.

The `.git` suffix suits hosts whose clone URLs end in it (GitHub,
GitLab, Bitbucket, Gitea). Azure DevOps clone URLs have none: with it,
users type the full URL.

== Endpoints

Two paths.

[cols="2,4",options="header"]
|===
|Endpoint |What it does

|`POST /v1/resolve`
|Translates `identifier` into the repository the rest of Kumoss
operates on.

|`GET /healthz`
|Liveness probe, answers `{"status":"ok"}`.
|===

== Request

[source,json]
----
{"identifier": "my-project"}
----

`identifier` is the only field. `additionalProperties` is `false`.

[cols="2,1,4",options="header"]
|===
|Field |Limits |Meaning

|`identifier`
|1-1024 chars
|The business identifier to resolve. Free-form by design.
|===

== Response

[source,json]
----
{
  "repo_url": "https://github.com/me/my-iac.git",
  "identifier": "my-project"
}
----

[cols="2,1,4",options="header"]
|===
|Field |Limits |Meaning

|`repo_url`
|1-2048 chars, required
|The `https://` URL Kumoss clones (scheme case-insensitive, host
required; the spec enforces the scheme with a `pattern`). Kumoss
clones, pushes and opens pull requests over HTTPS only, so SSH,
`git://`, `http://`, `file://` and local paths are off-contract and the
core answers `502` for them. When the identifier already is an
`https://` repository URL, it is passed through unchanged; an
identifier that cannot be mapped to one is `404`.

|`identifier`
|1-1024 chars, required
|The request's `identifier`, echoed verbatim. Normative rather than
conventional: callers correlate responses on it.
|===

`additionalProperties` is `false` on the response too, so a client can
rely on these two keys being the whole of it.

=== Status codes

[cols="1,5",options="header"]
|===
|Status |Meaning

|`200`
|Resolved.

|`400`
|The body could not be parsed at the transport layer — malformed JSON,
non-UTF-8 bytes, no `Content-Type`. May be a problem document or a
framework-default body.

|`401`
|Missing or invalid bearer token. Carries a `WWW-Authenticate: Bearer`
challenge.

|`403`
|The token is valid but not authorized for this endpoint.

|`404`
|The identifier is not in the catalog. The contract reserves this
for a clean negative answer, *distinct* from a transient backend
failure, which is a `5xx`.

|`422`
|Well-formed JSON that failed schema validation, including any field
other than `identifier` (such as the pre-2.0 `terraform_provider`).

|`502`
|The downstream catalog or CMDB returned an error.
|===

The `404`-versus-`502` split is the one design decision a catalog
implementation should get right: it is what lets the core tell a user
"no such project" instead of "try again later".

== How the core consumes the answer

`POST /api/v1/repository/parse` resolves the trimmed input through the
service before it clones anything. A `404` from the service reaches the
caller as `404` with the service's `detail`, so the wizard can tell the
user what to type instead. A timeout is `504`, and an unreachable
sidecar, any other error status, a body the core cannot parse, and a
`repo_url` that is not an `https://` URL are all `502`. There is no
silent fallback once the sidecar is enabled. The resolved URL is then
checked like any repository URI (no embedded password: `422`).

When the sidecar is disabled the core answers with an *identity
passthrough* and makes no call: `repo_url` and `identifier` both echo
the input, and anything that is not an `https://` URL is rejected with
`422`.

The same client checks a first IaC call's `project_identifier`: the
call is `422` unless the identifier resolves to its `repo_uri`, and the
service's own errors (`404`, `502`, `504`) reach the caller as above.
With the sidecar disabled an identifier resolves to itself, so only a
repository URL can be used, and that one is dropped as redundant. See
xref:main:reference/api/core.adoc#infrastructure-as-code[Core API].

== Providing your own implementation

A catalog-backed implementation looks the identifier up in a CMDB,
Backstage, or a shared spreadsheet and returns the canonical IaC
repository. The contract carries the result and says
nothing about where the lookup data lives. Point
`services.mapping.endpoint` at it (with `enabled: true`, the default),
set `KUMOSS_MAPPING_TOKEN` in `core/.env`, and drop the bundled
`mapping` service from your deployment; the core refuses to boot when
an enabled service has no endpoint or an empty token. Answer `404` with
a `detail` written for the end user when an identifier is not in the
catalog.

[#conformance]
== Conformance

The implementation-agnostic Schemathesis suite at
`contracts/conformance/mapping/` runs against any implementation of
this contract:

[source,bash]
----
cd contracts/conformance/mapping
uv sync
uv run pytest \
  --service-url=https://mapping.your.example \
  --service-token=$YOUR_TOKEN
----

`--service-token` is needed only if the implementation enforces
authentication.

The suite generates requests from the OpenAPI document and checks
schema conformance of the responses. It cannot check that the
identifiers your catalog resolves are the *right* repositories —
that is what the implementation's own tests are for.
