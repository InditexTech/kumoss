= Mapping sidecar API
:description: The contract that turns a business identifier into the repository to clone, plus a best-effort Terraform provider and cloud scope. Kumoss bundles no implementation; while it is disabled the core answers with an identity passthrough.

The mapping service answers one question: *given what my organization
calls this thing, which repository holds its IaC?* The identifier can
be a project name, a subscription code, a product slug, or a full git
URL — whatever the organization already uses. The service returns the
clone URL and, when its catalogue knows them, the Terraform provider
the identifier deploys with and the cloud scope it deploys into.

Only `repo_url` is guaranteed. `terraform_provider` and `scope_id` are
best effort, and *`null` means "I do not know"* — never "there is
none". A confident wrong answer is worse than `null`, so an
implementation returns `null` whenever its catalogue is not
authoritative.

NOTE: The web wizard no longer calls this service. The repository URL
is typed by the user, and the providers and scopes of a session come
from its root module and its
xref:main:reference/root-module-manifest.adoc[manifest] rather than
from a lookup. The contract and the core's
`POST /api/v1/mapping/resolve` route remain for other callers and
integrations.

Contract: `contracts/openapi/mapping.v1.yaml`, version 2.0.0. Kumoss bundles no
implementation of it: repository mapping is an optional extension point
you implement yourself and point `services.mapping.endpoint` at.
Bearer token: the value of the variable named by
`services.mapping.token_env`, `KUMOSS_MAPPING_TOKEN` by default. The
service is *optional* and ships disabled
(`services.mapping.enabled: false`, `endpoint: ""`).

It is internal-only. The browser never reaches it: the core forwards
requests through `POST /api/v1/mapping/resolve`.

== Endpoints

Two paths.

[cols="2,4",options="header"]
|===
|Endpoint |What it does

|`POST /v1/resolve`
|Translates `identifier` into the repository the rest of Kumoss
operates on, and optionally into the Terraform provider and cloud scope
the caller would otherwise have to ask the user for.

|`GET /healthz`
|Liveness probe, answers `{"status":"ok"}`.
|===

== Request

[source,json]
----
{"identifier": "my-project", "terraform_provider": "azurerm"}
----

Only `identifier` is required. `additionalProperties` is `false`.

[cols="2,1,4",options="header"]
|===
|Field |Limits |Meaning

|`identifier`
|1-1024 chars
|The business identifier to resolve. Free-form by design.

|`terraform_provider`
|enum, nullable
|The provider the caller already knows the deployment targets, by
Terraform provider type name — one of `azurerm`, `google`, `aws`,
`oci`, `kubernetes`, `vsphere`. Contract 2.0.0 renamed these from the
core's former vocabulary (`azure`, `gcp`, `vmware`). An
implementation may use it to disambiguate an identifier
that spans clouds, and must echo it back when it is sent. May be
omitted or sent as null, meaning the caller does not know either.
|===

== Response

[source,json]
----
{
  "repo_url": "https://github.com/me/my-iac.git",
  "identifier": "my-project",
  "terraform_provider": "azurerm",
  "scope_id": "0000aaaa-11bb-cccc-dd22-eeeeee333333"
}
----

[cols="2,1,4",options="header"]
|===
|Field |Limits |Meaning

|`repo_url`
|1-2048 chars, required
|The `https://` URL Kumoss clones (scheme case-insensitive, host
required; the spec enforces the scheme with a `pattern`). Kumoss
clones, pushes and opens pull requests over HTTPS only, so SSH,
`git://`, `http://`, `file://` and local paths are off-contract and the
core answers `502` for them. When the identifier already is an
`https://` repository URL, it is passed through unchanged; an
identifier that cannot be mapped to one is `404`.

|`identifier`
|1-1024 chars, required
|The request's `identifier`, echoed verbatim. Normative rather than
conventional: callers correlate responses on it.

|`terraform_provider`
|enum, nullable
|The provider the deployment targets. Echoes the request's value when
one was sent; otherwise the implementation's best-effort answer, or
`null` for "I do not know". Never a guess.

|`scope_id`
|1-1024 chars, nullable
|The cloud scope the deployment targets — `azurerm`: subscription id,
`google`: project id, `aws`: account id, `oci`: compartment OCID — as
a best-effort answer, or `null` for "I do not know". Same warning as
`terraform_provider`: never a guess.
|===

`additionalProperties` is `false` on the response too, so a client can
rely on these four keys being the whole of it.

=== Status codes

[cols="1,5",options="header"]
|===
|Status |Meaning

|`200`
|Resolved.

|`400`
|The body could not be parsed at the transport layer — malformed JSON,
non-UTF-8 bytes, no `Content-Type`. May be a problem document or a
framework-default body.

|`401`
|Missing or invalid bearer token. Carries a `WWW-Authenticate: Bearer`
challenge.

|`403`
|The token is valid but not authorized for this endpoint.

|`404`
|The identifier is not in the catalogue. The contract reserves this
for a clean negative answer, *distinct* from a transient backend
failure, which is a `5xx`.

|`422`
|Well-formed JSON that failed schema validation, including a
`terraform_provider` outside the enum.

|`502`
|The downstream catalogue or CMDB returned an error.
|===

The `404`-versus-`502` split is the one design decision a catalogue
implementation should get right: it is what lets the core tell a user
"no such project" instead of "try again later".

== How the core consumes the answer

The core calls the service from `POST /api/v1/mapping/resolve` and
surfaces a timeout as `504` and an unreachable sidecar as `502`. Two
more answers are also `502`: a body the core cannot parse, and a
`terraform_provider` outside the contract's enum (the generated client
hands the raw string through, and the core refuses it rather than
letting it fail later), and a `repo_url` that is not an `https://` URL.
There is no silent fallback once the sidecar is enabled.

When the sidecar is disabled (the shipped default) the core answers
with an *identity passthrough* and makes no call: `repo_url` and
`identifier` both echo the input, `terraform_provider` echoes whatever
was sent, and `scope_id` is `null`. Nothing is truncated and nothing is
guessed: sniffing `azurerm` out of a `dev.azure.com` URL would conflate
"hosted on Azure DevOps" with "deploys to Azure". This is exactly right for
users who paste real HTTPS git URLs already. Any other input is echoed
unchecked too; the next request that uses it as `repo_uri` is rejected
with `422`.

== Providing your own implementation

A catalogue-backed implementation looks the identifier up in a CMDB,
Backstage, or a shared spreadsheet and returns the canonical IaC
repository, plus the provider and scope when the catalogue is
authoritative for them. The contract carries the result and says
nothing about where the lookup data lives. Set
`services.mapping.enabled: true`, point `services.mapping.endpoint` at
it, and set `KUMOSS_MAPPING_TOKEN` in `core/.env`; the core refuses to
boot when an enabled service has no endpoint or an empty token.

[#conformance]
== Conformance

The implementation-agnostic Schemathesis suite at
`contracts/conformance/mapping/` runs against any implementation of
this contract:

[source,bash]
----
cd contracts/conformance/mapping
uv sync
uv run pytest \
  --service-url=https://mapping.your.example \
  --service-token=$YOUR_TOKEN
----

`--service-token` is needed only if the implementation enforces
authentication.

The suite generates requests from the OpenAPI document and checks
schema conformance of the responses. It cannot check that the
identifiers your catalogue resolves are the *right* repositories, nor
that a provider or scope it answers is true — that is what the
implementation's own tests are for.
