Nebula turns natural-language infrastructure requests into reviewed,
compliant Terraform-compatible code. Platform engineers and application
developers describe what they need; Nebula generates the code, validates
it against the target cloud, and audits it for compliance, then hands
over a pull request that a developer applies explicitly — every blocking
decision is computed by application code, never by a model.

== Key capabilities

[cards,columns="1 s:2 m:2"]
====
[card]
.xref:main:guides/make-a-request.adoc[Describe what you need, in plain language]
Open a session and phrase a request; Nebula fills in naming conventions,
resource defaults, and the placement it finds in your repository.

[card]
.xref:main:guides/generate-infrastructure.adoc[Get back validated Terraform code]
Nebula writes Terraform-compatible HCL on a new branch and runs it through
the engine's own `init`, `validate`, and `plan` until it passes.

[card]
.xref:main:guides/merge-and-apply.adoc#session-locked[Catch compliance issues before they ship]
An LLM auditor reviews every generated plan against your organization's
rules; a failing finding or a high-impact change locks the session until
a reviewer clears it.

[card]
.xref:main:guides/merge-and-apply.adoc[Apply only when a developer says so]
Nebula opens a pull request from the reviewed plan and applies it only
after an explicit apply request — never on its own.
====

== Frequently asked questions

More questions? See the full xref:main:faq.adoc[FAQ].

[accordion,aria-label="Frequently asked questions"]
--
.Where does Terraform state live?
[%collapsible]
====
Out of the box, Nebula keeps state itself, in a bucket dedicated to
state with one file per project. Your platform team can instead point it
at the remote backend your repository's own Terraform files declare.
Either way, your pull request never contains a state or backend file.
====

.Which cloud credentials does Nebula use?
[%collapsible]
====
The identity your platform team configured for the execution engine —
never yours. An optional external authorization service can also be
asked, at the start of each session, whether you may work on that cloud,
repository, and path.
====

.What data leaves Nebula when I make a request?
[%collapsible]
====
Your request text, the conversation, the repository files the agent
reads, the plan, and validation errors are sent to the language model
your platform team configured, and stored in the tracing system for
review.
====

.Do I have to open a pull request?
[%collapsible]
====
The API allows a direct apply, but the web application has no
standalone Apply button. As a `developer`, the pull request is your
route to apply — the recommended path, since it brings your team's
review and CI into the decision.
====

.Can other people see my sessions?
[%collapsible]
====
Only reviewers who hold a panel role (viewer, editor, or admin) can
read them, including the conversation. Nobody but you can continue,
merge, or apply your sessions.
====
